The general lesson, worth carrying: **a tree is not green because HEAD is green.** A
commit that adds a consumer without its producer can still leave the *final* tree perfect.

## 4. Incidents and corrections (all mine, all recorded)

1. **`node_modules` was destroyed and rebuilt.** The first verification harness linked the
   parent `node_modules` into temp worktrees with Windows directory **junctions**;
   `git worktree remove --force` followed the junction and deleted the repo's entire
   `node_modules` (0 entries). Detected when the pre-commit hook began failing
   `Cannot find module 'vitest/config'`; repaired with `npm ci` from `package-lock.json`
   (783 packages, exit 0). Commits 5-7 were refused during that window and re-committed
   after the repair. The harness is now junction-free (nested `.verify/tN` with no link),
   and `.verify/` plus its `.git/info/exclude` entry were removed afterwards — `git worktree
   list` shows only the operator's checkout. **Caveat that outlives this session: the
   working `node_modules` is a rebuild from the lockfile, not the original install.**
2. **A probe reading was wrong before it was a finding.** A literal grep for
   `AT TIME ZONE 'America/New_York'` in migration 0040 returned 0 and looked like a
   contradiction of the FID's 119-column claim. The migration applies the zone dynamically
   from the VALUES tuple (`USING (%I AT TIME ZONE %L)`), so the literal never appears. The
   artifact was right; the probe was wrong. Recorded in FID-001 §8 rather than quietly
   dropped, because "the check that looked alarming" is exactly what a later reader will
   re-run.
3. **One ledger edit went to the wrong anchor and was reverted.** A `VERSION` bump was
   issued as a second replacement in a call scoped to `CHANGELOG.md`; the anchor `0.0.31`
   matched inside the `0.0.31` *header*, corrupting it to `## [0.0.32\n] — 2026-09-19
   session`. Caught by grep before staging (the `0.0.31` header had disappeared), reverted,
   and `VERSION` written on its own. `git diff --numstat CHANGELOG.md` → 23 insertions,
   **0 deletions**, confirming the revert was complete. Lesson: a bare version string
   followed by a newline is not a safe anchor — it matches header text.

## 5. Open decisions carried forward (operator-only)

1. **The status-vocabulary gap — still open, and now the most likely to recur.** The
   protocol allows `created | analyzed | fixed | verified | loop-complete | closed`, and
   `closed` requires a G2 commit (G2). There is **no lawful value for *fully implemented,
   gates green, not yet committed*** — both FIDs sat in that state, were parked on
   `verified` (which the spec describes as "an intermediate status for partially-executed
   work"), and each recorded the misfit honestly. Closure resolved *these two* FIDs; it did
   not resolve the gap. Any future implementation landing before its commit lands in it
   again. Options: add a status (e.g. `implemented` as a first-class value, with `closed`
   still gated on G2), or amend G1 so an approved level-3 session can commit its own
   verified work and the gap never opens.
2. **`dev/fids/FID-20260917-005` is live in `dev/fids/` but is terminal.** It is a finding
   record (`analyzed (premise dissolved)`, zero code delta, §6 "loop record: not
   warranted"), and SCOPE row 78 already records it as `Closed — no-action finding`. Under
   the current rules it can be neither archived (archival is only at `closed`, which
   requires a commit hash) nor honestly left reading as active work. Same gap as §5.1, with
   a no-code-delta shape. Recommend an explicit no-action dispositions status rather than
   inventing a hash.
3. **Fourteen archived FIDs still carry the legacy string**
   `loop-complete (filed + implemented…)`. Left alone deliberately under the same-session
   amendment that forbids re-opening archived files; flagged here so it is a decision, not
   an oversight. The six FIDs whose *active* duplicates were byte-identical were corrected
   and de-duplicated in commit 2.
4. **`policy.adminLogDays` is inert** (FID-20260923-002 §7): `cleanupOldLogs` computed
   `adminCutoffDate` and never read it, so admin logs are never purged. The dead arithmetic
   was removed and the defect recorded; implementing the purge is a **data-retention
   product call**, deliberately not guessed.
5. **Optional determinism:** the process `TZ=UTC` pin from FID-20260923-001 §5.7 is safe
   only after the migration and was deliberately not applied — it is reversible-by-default
   and couples no app behaviour to a host env change. Available whenever the operator wants
