The same gate over the same two SHAs reported **clean** locally ~90 seconds earlier. Root cause, found in `scripts/invertedRouteCensus.cjs:153`:

```js
const w = WAIVERS.find((x) => c.file.endsWith(x.file.replace(/\\/g, '\\')) && c.raw.startsWith(x.rawPrefix));
```

The waiver is keyed on `'components\\admin\\PlayerDetailModal.tsx'` — literal backslashes — while `c.file` comes from `path.relative()`, which yields backslashes on Windows and **forward slashes on Linux**. The `.replace(/\\/g, '\\')` is a **no-op** (backslash replaced by backslash), so the intended normalisation never happens. The waiver therefore fires only on Windows. Reproduced byte-for-byte by forcing POSIX separator semantics locally:

```
routes: 240 · call sites: 301 (unparsed: 0)
=== WAIVED (0) — documented false positives ===
=== MISSING (1) — called but no route matches ===
  components/admin/PlayerDetailModal.tsx:267  /api/admin/vip/${action}
POSIX CENSUS EXIT=1
```

The chain is fail-fast (`exit 1` per gate), so **gates 3-10 have never executed on GitHub**; CI has exercised Gate 1 only. Two other divergences are now measured rather than assumed: CI ran **Node v24.21.0 / npm 11.19.0** (`node-version: lts/*` → `/opt/hostedtoolcache/node/24.21.0`) against this host's 25.2.1, and both runs carry the Node-20-deprecation annotation for `actions/checkout@v4` / `actions/setup-node@v4` plus the `ubuntu-latest` → Ubuntu 26 notice (2026-10-19).

Method note, recorded because the first attempt lied: the shim used to simulate POSIX paths initially patched only `path.relative`. That "found" a second broken gate — `hostTimezoneCensus` flagging `lib/gameTime.ts`, the module it explicitly exempts — because a script comparing `path.relative()` to `path.join()` is self-consistent on any single platform, so patching one and not the other fabricates failures. A second attempt was also wrong: reassigning `path.sep` corrupts Node's internals on Windows (`path` **is** `path.win32`), and `relative()` returned `..C:/Users/…`. The faithful version translates the *results* of `join` and `relative` only. With that, the simulation shows **exactly one** Linux-hostile gate (Gate 1); gates 3-7 all pass under POSIX separators. This is the finding the first two shims nearly turned into a false one.

### 3.3 The auto-farm cause (Directive B)

Grounding the complaint against the code (not the report) produced the mechanism, with a verified chain at every hop:

- `lib/harvestService.ts:123` (pre-fix) — `canHarvestTile` refuses any terrain outside `Metal, Energy, Cave`:
  `if (![TerrainType.Metal, TerrainType.Energy, TerrainType.Cave].includes(tile.terrain)) return false;`
- `lib/caveItemService.ts:485` — `harvestForestTile`, the **only** path a forest payload can be paid out through (`/api/harvest` dispatches `Forest` → `harvestForestTile`; no other caller exists), gates on that function and returns `'You have already explored this forest. It will refresh later.'` before writing any harvest record.
- `components/TileRenderer.tsx:163-173, 392-395` — the chip is green `ready` whenever `isTileFarmable(terrain) && !isPlayerOnCooldown()`, and `isPlayerOnCooldown()` is "does the tile's log contain a record for me". Since no record is ever written, the chip can never leave `ready`.
- `utils/autoFarmEngine.ts:987` — the engine advertises the same four terrains (`['Metal','Energy','Cave','Forest']`), so it POSTs, is rejected, and still pays Basic-tier `HARVEST_DELAY_EXTRA` (2000 ms).
- `lib/mapService.ts:444` — `{ terrain: TerrainType.Forest, weight: 2 }` ≈ 2% of the map (~450 of 22,500 tiles).
- Advertised everywhere else: `lib/tileMessages.ts:81`, `app/help/page.tsx:41,179,215,259`, and `harvestForestTile`'s own docstring (`BETTER rewards than caves!`).

Conclusion: the reported symptom is exact, and its cause is a guard list that was never updated when Forest acquired a payout path — so ~450 tiles read permanently `ready` and yielded nothing, for every player, through every harvest path.

## 5. Out-of-scope discoveries

Recorded, not worked — each is cross-referenced to a `SCOPE.md` entry so it survives as a decision rather than an omission.

1. **CI is red on `main`, for a Windows-only gate.** `scripts/invertedRouteCensus.cjs:153`'s no-op `.replace(/\\/g, '\\')` makes the waiver match only on Windows, so Gate 1 can never be green on `ubuntu-latest`; `gate-chain` has consequently never executed gates 3-10 anywhere. The local green the ledger has recorded all arc was a one-platform verdict. Filed as `[OPEN-OUT-OF-SCOPE]` item 66 (§3.2).
2. **`dev/tmp/` is a gate blind spot.** Gitignored, but not excluded from `tsc`/`eslint`, so an abandoned artifact there poisons the Law-3 gates while staying invisible to `git status` — demonstrated twice in one session. `SCOPE.md` row 128.
3. **"Which terrains are farmable" exists in four places** — the eligibility guard, the route's dispatch chain, the engine's `harvestableTerrains`, and the viewport's `isTileFarmable`. This defect is one of their disagreements; the class is the decision, not the one word. `SCOPE.md` row 129.
4. **Auto-farm cannot report what it collected.** The engine never assigns `metalCollected`/`energyCollected`/`caveItemsFound`/`forestItemsFound` (`grep` over `utils/autoFarmEngine.ts` → no output), `mergeSessionIntoAllTime`/`saveAllTimeStats`/`resetAllTimeStats`/`getStatsSummary`/`calculateEfficiency` have no callers outside their own module, and the game page holds both stats shapes in discarded setters. There is no resource counter in the auto-farm surface, which is *why* a total harvest failure could read as a vague impression. Related: the chip's `isPlayerOnCooldown()` ignores `resetPeriod` where the server compares it, so the cooldown it does report can be permanently stale. `SCOPE.md` row 130.
5. **VIP pacing sits at the movement rate limit.** `ENDPOINT_RATE_LIMITS.movement` is 120/min and VIP `MOVEMENT_DELAY` is 300 ms, so a 429 there is indistinguishable from "nothing to collect" (the engine treats a failed move as a skipped tile). Unproven — a boundary to watch, not a claim. Noted inside row 130.
6. **`"publish"` has no artefact.** `git tag -l` returns only `v0.0.1`; no workflow creates tags or releases, so releases 0.0.32-0.0.37 exist as CHANGELOG/VERSION records on the remote, not as tags (§3.1).

Not one of these was folded into the Forest fix; each changes a gate's contract, a product surface, or a build setting, and none was named by either directive.
