**Date:** 2026-09-17 · **Protocol:** ECHO v0.1.2 single-agent (16 laws) · **Branch:** `main`
**Operator question:** is the Stripe VIP mapping through players.mongoId actually
populated for pg-era players, and are VIP grants silently failing for new accounts?

## Answer: yes it is failing — and worse than "for new accounts": for ALL accounts

- **Cohort probe (66 players):** `mongo_id` populated for **zero** — nothing
  writes it post-pivot (write-side grep empty), no backfill ever ran.
- All four money functions key on `eq(players.mongoId, userId)` while checkout
  metadata embeds **username** as userId — the lookup can never match.
- **Failure modes per caller:** `verify-session` (primary path) returns 500 to
  the customer after capture (loud, at least); the **webhook logs "VIP granted
  successfully" on the false return** and records the payment transaction
  anyway — Stripe gets 200 and never retries. That is the silent loss.
- No incident history only because `paymentTransactions` has **0 rows** — no
  completed checkout has ever run in this environment. A loaded trap, not a
  past loss (in dev).
- The lone `vip=1` (fame, expires 2027-09-11, tier NULL, no Stripe IDs) is
  fully attributed: `mod_log` shows `VIP_GRANT` by fame on 2026-09-11 via the
  admin endpoint, which correctly looks up by **username**. Admin + referral
  VIP paths are healthy — only the Stripe path is dead.
