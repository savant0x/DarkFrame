# SESSION-2026-09-17-043 — Clan detail GET rebuilt (FID-20260917-006): operator bug fixed

**Date:** 2026-09-17 · **Protocol:** ECHO v0.1.2 single-agent (16 laws) · **Branch:** `main`
**Operator report (screenshot):** created a clan ("Savant"); clicking it from the
sidebar spins forever and toasts **"Failed to load clan data"**.

## Root cause (probed, not guessed)

`ClanManagementView.tsx:72` and `ClanPanel.tsx:87` fetch `GET /api/clan/${player.clanId}`
and require `data.success` — but **that route never existed**: 42 routes live under
`app/api/clan/`, none `[id]`, and `git log --all -- 'app/api/clan/[id]/route.ts'` is
**empty** (not even deleted — planned, client-written, never built). The toast is both
failure paths (non-success JSON on a 404, and the catch) collapsing into one message.
Class note: the 237-route dead-route census (session 037) swept existing-but-uncalled
routes; this is the inverse class — **called-but-never-built** — which no census had
covered. The service layer survived intact (`getClanById` → full `rowToClan` shape:
members inline, level, settings, stats), so the fix is a thin route.

## What shipped

- `app/api/clan/[id]/route.ts` — requireAuth → getClanById → `{ success, clan }`;
  null → `CLAN_NOT_FOUND` (404 via the codes map); throw → 500 envelope. Bare handler
  (no `withRequestLogging`: its params typing conflicts with Next 16 dynamic routes;
  the newest dynamic sibling runs bare too). Auth: any signed-in player (join preview
  needs it; payload is public-class).
- `__tests__/api/clanDetail.test.ts` — 4 pins incl. the exact consumer reads
  (`members[0].username` for the view's member gate at :720, `level.currentLevel`
  for the header at :742); real error-envelope helpers, only the two collaborators
  mocked.
- `scripts/e2eClanDetail.ts` — live driver: binds to an EXISTING player (players has
  NOT NULL walls; seeding players is createPlayer's job), seeds/deletes only a probe
  clan, mints a real JWT, drives the handler directly, explicit `process.exit`
  (open-pool hang lesson).
