## Addendum (2026-09-25) — the `CHAIN EXIT=0` line in §4.2 came from the wrong process

§4.2 pasted `CHAIN EXIT=0` from `echo "CHAIN EXIT=${PIPESTATUS[0]}"` placed after
`printf … | bash .githooks/pre-push … | tail`. `PIPESTATUS[0]` is **`printf`'s** status — the status of the
process that fed the hook, not the hook's. The run's *verdict* was independently true: the pasted output ends
`✅ pre-push: attribution scan clean`, which the hook prints only on success, and the chain's refusal text is
unmistakable when it fires. But the exit-code claim was not what it appeared to be, and a record that keeps a
measurement it now knows was mis-taken is exactly the failure this whole arc has been about.

Re-measured the same day from the hook itself, using the capture form
`out="$(printf … | bash .githooks/pre-push …)"; echo $?`: green → `CHAIN EXIT=0`, a deliberate violation →
`HOOK EXIT=1`. The bug was fixed in the measuring script, and filed as `FID-20260925-002` §2 finding 5 rather
than corrected quietly — the lesson generalizes past this file: **a check that looks like a verdict must be
probed before it is trusted**, which is the same class as `FID-20260923-001` §8's `AT TIME ZONE` probe (a
correct artifact behind a wrong probe). This addendum is appended rather than rewritten into §4.2, following
the directory's own rule: a session summary is append-mostly, and a correction that erases its own trail would
be the defect it documents.
