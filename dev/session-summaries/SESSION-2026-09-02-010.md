## Law 1 evidence (pre-implementation)

**Render contract (session-008, fully re-read):** fetch is `GET /api/admin/clan/analytics?clanId=&tab=`; consumer reads `data.clan` (domain `Clan`) and `data.analytics`. Per-tab fields: Overview (`totalPower`, `alerts[].message`, 4× `recentActivity.*`), Financial (`totalDeposits`, `totalWithdrawals` — the tx table itself stays stubbed client-side), Activity (`activities[]{description,timestamp,type}`), Alliances (`alliances[]{clanIds,createdAt,terms}`), Health (`healthScore`). Members/Territory/Warfare/Research render purely from `clan` — but Territory reads `tileX/tileY/defenseBonus` while DB stores `x/y` (mapping + computation required) and Members renders `contributedRP`/`contributedResources` enrichment.

**Data sources verified:**

- `clans` row (schema `lib/db/schema/clans.ts`): snake_case columns, jsonb `members/activePerks/territories/bankTransactions` (`$type<any[]>`), decimal tax rates, int treasury. Row→`Clan` mapping is established house practice (`clanService.ts` line ~904, `bankService.ts` line ~85).
- `clan_activities`: canonical columns `clan_id, activity_type, player_id, username, details, timestamp` (5 services). Activity types match `ClanActivityType` (BANK_DEPOSIT, BANK_WITHDRAWAL, MEMBER_JOINED/LEFT/KICKED, TERRITORY_CLAIMED, WAR_DECLARED…). **territoryService's 3 inserts use `type`/`metadata` — divergent, likely-broken columns** (recorded as SCOPE #16, NOT fixed here).
- `clan_alliances`: columns per `clanAllianceService.rowToAlliance` — `id, clan_ids (JSON string), type, status, proposed_by, proposed_at, contracts, cost, broken_at…`; `metadata` jsonb may carry terms. `Alliance` domain type has NO `terms` field (optional-contract).
- `ClanBankTransactionType` enum: `DEPOSIT`, `WITHDRAWAL`, `TAX_COLLECTION`, … (types/clan.types.ts 395–402). `ClanBankTransaction.amount.metal/energy/researchPoints` — deposits sum metal+energy+RP.
- Member jsonb: `ClanMember { playerId, username, role, joinedAt, lastActive }` (clanService 276).
- `getDefenseBonus` is exported from `lib/territoryService.ts` (used for per-tile computation).
- Auth house pattern (bot-stats route): `getAuthenticatedUser()` → null check → `tokenPayload.isAdmin !== true` → `createErrorResponse(ErrorCode.ADMIN_ACCESS_REQUIRED, …)`, wrapped in `withRequestLogging(rateLimiter(handler))` with `createRouteLogger` + `ENDPOINT_RATE_LIMITS.admin`.

**Design decisions (recorded):**

1. Clans row, activities, alliances all read via **raw SQL** — avoids adding new dialect-purgatory tsc errors (the MySQL schema types against the pg driver), keeping tsc at 2,039.
2. ONE row-extraction seam (`getQueryRows`), typed for today's node-postgres runtime (`QueryResult` → `.rows`) with a single documented line for FID-20260902-001 to flip.
3. `contributedRP`/`contributedResources` enrichment **omitted** — zero writers exist in the codebase; faking them would fabricate data. Modal renders their `|| 0` fallbacks (existing behavior for missing optional fields). Recorded as future enhancement.
4. Alerts/healthScore derived from real signals only (inactivity, treasury, membership, 24h activity); the Health tab's hardcoded bars stay client-side presentation (out of the route's contract).
