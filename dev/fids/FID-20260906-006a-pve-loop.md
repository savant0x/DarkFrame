## 1. Summary

FID-006 finding F4: **no player→bot combat loop exists** — bot armies are empty
(`botService.createBotPlayer` writes `units: []`, scalar `totalDefense`), no route resolves a
player attacking a generic bot, and the Beer Base attack route (`/api/combat/attack`) both
fails to fight (garrison = empty array) and **never credits the loot it announces**. This FID
repairs the reachable slice of the PvE loop (Beer Bases — the designed high-value targets)
with real combat, real loot, and the doc's 3× multiplier, then runs the FULL loop to
convergence before any code lands.

Out of scope (logged, not built here): generic-bot attack route (P6's broader half), PvE XP
source enumeration beyond the doc's base-raid values, bot vs player (botCombatService shim —
FID-005 §5.3).

## 3. GREEN design (doc-faithful, Postgres-native)

1. **Synthesized garrison** (route, not schema): when `base.units` is empty, build a
   `Unit[]`-shaped garrison from the base's tier: per-tier unit count × defense-only units
   (defense 20/each, HP 15/DEF unit), totalDEF matched to `totalDefense`. Resolves via the
   unmodified `resolveBattle` — real rounds, real risk, doc combat math. `battleLog.defender`
   stays the base's username; nothing writes to bots.
2. **Loot crediting (R1):** on ATTACKER_WIN — credit the attacker
   `base.resourcesMetal/Energy × resourceMultiplier` (3× from `getBeerBaseConfig()` default),
   using the battleService BigInt pattern (`BigInt(Number(x) ± amount)`); remove the base
   (R3 replacement: direct drizzle delete of the `players` row gated on
   `isBot AND isSpecialBase` — same semantics as `removeBeerBase`, shim-free); analytics
   event unchanged.
3. **Config repair (R4):** rewrite `getBeerBaseConfig()`/`updateBeerBaseConfig()` onto the
   drizzle `gameConfig` table (exists in schema; verify column shape before wiring) so the
   admin panel's Beer Base settings (incl. 3×) actually persist and are read. **P7 delivered.**
4. **Rewards (R5):** `BASE_ATTACK_WIN` (400 XP) on victory, `BASE_ATTACK_LOSS` (60 XP) on
   defeat — both via `awardXP` (already applies flag-bearer doubling). Drop the invented
   flat reward from the payload; keep `rewards.resources` as the credited loot.
5. **Loss path:** on repel, message reflects the real garrison; battle still persisted +
   notified; no base mutation.
6. **Presence, rate-limit, auth:** untouched (already DB-position-enforced).
