## 1. Summary

The auto-farm system has a complete statistics subsystem — a typed session shape, a typed all-time shape, a localStorage persistence layer with merge/reset/summarise/efficiency helpers, an engine that publishes stats on a 1-second tick, and a page that subscribes to them — and **it reports zero for every resource it collects**.

`AutoFarmSessionStats` (`types/autoFarm.types.ts:78`) declares four collection counters: `metalCollected`, `energyCollected`, `caveItemsFound`, `forestItemsFound`. **Nothing ever assigns them.** `grep -n "metalCollected\|energyCollected\|caveItemsFound\|forestItemsFound" utils/autoFarmEngine.ts` returns **no output**; every one of the engine's nine `updateStats` call sites writes only `tilesVisited`, `errorsEncountered` or the three attack counters. The data is not merely available — it is **already in hand and already parsed**: `attemptHarvest` reads the authoritative gains off the harvest response (`const metalGained = Number(data.metalGained ?? 0)`, `:1021`), emits them on the `harvest` event (`:1030-1039`), and returns them. They are then thrown away, because the only thing that updates the counters is `updateStats`, and no call site passes them.

The item half fails the same way, one layer deeper. Cave and forest items are unobservable because the engine reads a field the HTTP response never carries:

```js
console.log(`[AutoFarm] Harvest ok: … ${data.itemFound ? `, item=${data.itemFound}` : ''}`);   // :1023
…
itemFound: data.itemFound                                                                        // :1035
```

`/api/harvest` builds `itemFound` only for its **own internal log line** (`app/api/harvest/route.ts:229`, inside `resultSummary`) and returns `item` — the full object — in the response body (`:240`). The engine's `data.itemFound` is therefore always `undefined`. TypeScript could not catch the mismatch because `AutoFarmEventData` carries an `[key: string]: unknown` index signature (`types/autoFarm.types.ts:135`), which accepts any field name on any emitted payload; the annotation says "kept open-ended because the engine evolves payloads per type", and the cost of that openness is that the payloads are unchecked.

Downstream, the numbers are discarded a second time. `app/game/page.tsx:180-181` holds both stats shapes in **discarded setters** (`const [, setAutoFarmSessionStats] = useState(…)`), so the engine's `onStats` callback (`:298-300`) writes into state nothing reads, and `loadAllTimeStats()` (`:366-367`) does the same for the all-time shape. The persistence layer is correspondingly unreachable: `mergeSessionIntoAllTime`, `saveAllTimeStats`, `resetAllTimeStats`, `getStatsSummary` and `calculateEfficiency` have **zero callers outside their own module**. And no surface renders any of it — `components/AutoFarmPanel.tsx` shows Status, Position, Tiles, Last action and Speed tier; `AutoFarmStatsDisplay` was archived as dead UI on 2026-09-19 (`dev/archives/2026-09-19-dead-ui/`).

**Why this is the FID that matters.** `FID-20260925-003` fixed a total, permanent Forest harvest failure — ~2% of the map, every player, every path — and it was **reported as a vague impression** rather than a defect, because the instrument that would have shown "0 resources collected across 450 tiles" was itself permanently reporting 0. Row 130 says it plainly: *"Auto-farm cannot report what it collects — which is why a total harvest failure read as a vague impression."* The visibility defect is the reason the functional defect survived. This FID builds the instrument.

There is a second, independent leak on the same path, found while grounding: the `harvest` event carries `method: 'direct_api'` and **no `key`**, but `app/game/page.tsx:280-285` renders the live label from `data.key` — so the operator's only real-time feedback during a sweep reads `⛏️ Harvesting Metal (pressed '?')` with the actual gains dropped at the UI boundary, even though `attemptHarvest` had just put them in the event payload.

### 2.4 Call-graph notes (Law 4)

A real runtime path from the sweep to the discarded number, with the break at each hop.

`AutoFarmPanel` "Start" → `app/game/page.tsx` `engine.start()` → `processNextTile()` → `processTile(pos)` → `attemptHarvest(pos, tileInfo)` (`utils/autoFarmEngine.ts:982`) → `POST /api/harvest` → `app/api/harvest/route.ts` `harvestResourceTile` / `harvestCaveTile` / `harvestForestTile` → response body `{ success, metalGained, energyGained, item, bonusApplied, xpAwarded, …, harvestStatus }` → back in `attemptHarvest`: gains extracted at `:1021-1022`, **event emitted `:1030-1039`, `updateStats` never called with them** → the engine's `stats` object keeps four zeros → `startStatsTimer()` fires `updateStats({})` every 1000 ms (`:527`), which re-publishes the same four zeros via `onStatsCallback` → `engine.onStats` (`app/game/page.tsx:298`) → `setAutoFarmSessionStats` → **the discarded setter (`:180`)** → and even the one-reader path (`loadAllTimeStats` at `:366`) lands in the discarded all-time setter (`:181`).

Two of the six hops are *live and correct* (`processTile` → `attemptHarvest` → the response parse); the break is entirely between "the number is in a local variable" and "the number is in `this.stats`". Nothing is unwired in the usual sense — the wire exists and terminates in a state binding with no reader, which is why this presents as silence rather than an error.

## 3. Impact Analysis

- **Who/what is affected:** every auto-farm run, on both tiers, for every player. The all-time totals in `localStorage` (key `darkframe_autofarm_alltime_stats`) can only ever contain zeros for resources and items, so the persisted history is structurally false rather than merely stale.
- **Failure modes if unfixed:**
  1. **A total functional failure reads as a vague impression.** This is not hypothetical — it is the recorded history of FID-20260925-003 (row 130). With no counter, a player cannot distinguish "the sweep is working" from "the sweep collects nothing"; the only non-zero signals (`tilesVisited`, `errorsEncountered`) are precisely the ones a *working* harvest also produces.
  2. **The persisted all-time record is a lie with a plausible shape.** `loadAllTimeStats` → `mergeSessionIntoAllTime` sums session counters into all-time totals; with the session counters pinned at 0, every field the subsystem exists to accumulate is 0 while `totalTilesVisited` and `totalTimeElapsed` grow. A statistics surface that reports `'12 sessions | 3h | 0 resources'` is more misleading than no surface, because it looks like a valid measurement.
  3. **Regression detection is impossible at the surface where the previous defect occurred.** The Forest failure was invisible to the UI and visible only to a grep; a counter would have made it visible to the player in one session.
- **Blast radius of the fix:**
  - **Direct:** `utils/autoFarmEngine.ts` (counter writes in the existing success branch + one pure mapping helper), `types/autoFarm.types.ts` (declare the payload fields the engine actually emits; remove the index signature that hid the mismatch), `app/game/page.tsx` (two setters gain value bindings; pass stats to the panel; on `complete`, merge into all-time and reset), `components/AutoFarmPanel.tsx` (render a Collected block).
  - **Transitively:** `mergeSessionIntoAllTime`/`saveAllTimeStats`/`getStatsSummary` gain their first external callers, which is what turns three exported-but-dead functions into live code. **No new export is introduced except one pure mapping helper**, which the Perfection Loop's caller check requires to have a production call site (§6).
  - **Explicitly out of scope, recorded rather than implied:** the viewport readiness chip computing its own cooldown (row 130's adjacent item); the four-copy "farmable terrains" drift (row 129); VIP `MOVEMENT_DELAY` 300 ms against `ENDPOINT_RATE_LIMITS.movement` 120/min (row 130, unproven boundary). None is touched here; each has its own decision.

## 4. Five Questions

| Question | Answer |
| -------- | ------ |
| Works for ALL cases, not just the common case? | Yes, and the design choice that buys it is *where the number comes from*. The counters are incremented **only from the authoritative response body** (`metalGained`/`energyGained`/`item`), never from a local intention, so the session totals cannot disagree with what the server actually granted — and a rejected harvest (`data.success === false`, cooldown/depleted) returns before the increment block, so a refusal cannot be counted as a collection. The terrain→counter mapping covers all four advertised terrains explicitly: Metal/Energy accumulate resources; Cave/Forest accumulate items, keyed on the item actually returned, so a Forest tile that yields no item does not inflate `forestItemsFound`. Pinned by a unit test over the pure helper for every terrain, including the item-less case. |
| Scales? | Yes. Four integer increments per **successful harvest** — not per tile, not per tick — against a loop that already performs one HTTP round-trip per harvest and a 300–500 ms pacing delay per tile. The stats object is a flat struct spread-rebuilt on each update (`:198`), unchanged in shape. No new query, no new network call, no new listener: the counters ride the `updateStats` call that the success branch already makes implicitly through the tick timer, and the readout reads the state the page is already setting. The one added consumer is a render of four numbers in a panel that already re-renders on every state tick. |
| Survives a hostile attacker? | The change is client-side telemetry and **must not be mistaken for authority.** Nothing added here is trusted by the server, gates any action, or is written back to the database: `/api/harvest` remains the sole grantor (the route already feeds `detectResourceHack` and `detectCooldownViolation`, and those rails are untouched), and the counters are derived from the server's own response rather than from player input. The one genuine hardening is on the *type* boundary: removing `[key: string]: unknown` from `AutoFarmEventData` converts a class of silently-wrong payloads into compile errors — the exact failure that let finding 6 ship past `tsc`. Tightening a type that was hiding a defect is a strict improvement in the anti-tamper sense: the client's own reporting surface can no longer be quietly fed a field name that nothing produces. |
| Maintainable in 2 years? | Yes, and this is where the fix earns its keep — but the honest answer is that it depends on one deliberate control. The mapping is a single pure helper (`applyHarvestGains`) so the rule "which counter does this terrain feed" lives in exactly one place and is unit-testable without driving the 1302-line engine loop. That matters *because of* `SCOPE.md` row 129: "which terrains are farmable" already exists in four copies, and this change must not become a fifth. The helper deliberately knows **nothing** about the farmable-terrain list — it maps gains onto counters for whatever terrain the caller reached — and the FID records that constraint at the site so a future author cannot fold the two together by accident. The declared-field change makes the payload contract checkable by the compiler instead of by review. |
| Sets the standard for the industry? | Yes, and the transferable lesson is the uncomfortable one: **an observability surface is a functional feature, not a nicety — its absence is what converts a defect into a vibe.** The Forest failure was a 100%-broken feature that read as "feels off", and the reason was that the only layer built to notice it was permanently reporting zero, in a subsystem with a complete type, a storage key, a merge function and a stalled tick — every part present except the assignment. "The counters are all there, they're just never written" is a specific, recognisable, generalisable failure mode, and the response that generalises is not "write the counters" but "prove the instruments read non-zero when the feature works" — which is what the new test does by asserting an exact non-zero delta from a mocked authoritative response. |

All five are `yes`. No redesign required.

## 5. Proposed Fix (GREEN)

### Approach

**Record the counters where the authoritative number already exists; keep the mapping in one pure helper so it cannot become a fifth copy of terrain knowledge; declare the event payload fields so the compiler checks them; give the session and all-time shapes real state; render them; and test the delta, not the plumbing.**

The load-bearing insight is that `attemptHarvest`'s success branch is the *only* place in the engine that holds a server-granted amount. Putting the increments there means all three harvest entry points (`processTile`'s dispatch, the combat path's absence of one, and any future caller of `attemptHarvest`) are covered by construction, and nothing must be kept in sync by hand.

### Alternatives considered

| Alternative | Why rejected |
| ----------- | ------------ |
| Increment the counters from the `onEvent`/`onStats` callback in `app/game/page.tsx` instead of in the engine | Puts the accounting rule in the consumer, so a second consumer (or a panel test, or a future export) gets its own opinion — the same "N copies of one rule" shape that caused `SCOPE.md` row 129. It also widens the counter updates across a React state boundary, which is the wrong lifetime for a per-session aggregate the engine already owns |
| Compute the counters from `player.resources` diffs (before/after `/api/player`) | Reintroduces exactly the polling that FID-20260911-047 removed (~350 KB per harvest cycle) and derives the number from a *derived* state rather than the grant itself, so it would count unrelated resource changes (trades, rewards, other tabs) as harvests |
| Fix the mismatch on the server: add `itemFound` back to the harvest response | Treats the response body as the thing to change when the *engine* is the side holding a stale assumption: `item` is the documented field (the route's own docstring lists it), it carries strictly more information (name, rarity, id), and adding a second redundant name for the same value creates the drift this FID is about. The engine is corrected to read the documented field |
| Keep `[key: string]: unknown` on `AutoFarmEventData` and merely declare `itemFound` | Fixes finding 6 and leaves the mechanism that hid it: with the index signature in place, the *next* undeclared payload field is equally invisible. Declaring the fields **and** removing the signature is what makes the compiler a participant. Bounded by a mechanical rule — `tsc` enumerates every payload that then needs a declared field, and each is a real emitted shape, not an invention |
| Drive the engine's loop in tests (fake timers + mocked `fetch`) to assert the counters end-to-end | Brittle and slow: the loop is a recursive `setTimeout` chain with `await new Promise(setTimeout)` pacing, an interval stats timer, and a persisted-run scheduler. The test would assert timer choreography as much as accounting, and would be the flakiest test in a 1325-test suite. A pure helper plus an explicit note that end-to-end coverage is unwired states the gap instead of papering over it |
| Revive `AutoFarmStatsDisplay` from the archive instead of rendering in `AutoFarmPanel` | It was archived as dead UI on 2026-09-19 as part of a deliberate sweep, and its markup predates the FID-20260906-012 Phase 2-R1 panel rebuild — reviving it would reintroduce a second, visually inconsistent auto-farm surface. The panel is where the operator already looks; the readout belongs there |
| Retire the stats subsystem as dead instead of wiring it | The other admissible branch of row 130, and rejected on the evidence: the counters are cheap to make true (the number is already in a local variable at the moment it is discarded), and the subsystem's absence is the recorded *cause* of the previous defect going unnoticed for as long as it did. Retiring it would delete the instrument rather than build it — and would still leave `getStats()` returning a `stats` object whose four fields are permanently misleading to any future reader |
| Also fix the viewport readiness chip (row 130's adjacent item) in the same change | Different file, different semantics (server-vs-client cooldown computation, `resetPeriod` matching), and the same reason FID-20260925-003 declined to fold row 129 in: it edits a display predicate whose correct behaviour is a product decision about what "ready" means when the server disagrees. Recorded, not smuggled |
