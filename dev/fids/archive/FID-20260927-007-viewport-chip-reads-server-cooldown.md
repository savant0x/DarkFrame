# FID-20260927-007: The readiness chip invents its own cooldown — the server's answer is computed, returned, and thrown away

## 1. Summary

Two live, player-visible cooldown indicators each compute the harvest cooldown **from their own private rule**, and both rules are wrong in ways the server never sanctioned. `components/TileRenderer.tsx`'s NEON NOIR chip decides "am I on cooldown?" by matching `lastHarvestedBy` on `playerId` **alone** — dropping the `resetPeriod` half of the server's rule — and then computes the countdown from host-local `setHours(12/24)`, the exact host-timezone class FID-20260923-002 was built to kill. `components/TileHarvestStatus.tsx` is worse: a flat `HARVEST_COOLDOWN_MS = 5 * 60 * 1000` that **exists nowhere in the server** (measured, §2 finding 5). Meanwhile the server's real answer is computed on every harvest (`getHarvestStatus` → `canHarvestTile`), returned in the `POST /api/harvest` response body, and **discarded by the client on the very line that renders the result** — and a dedicated `GET /api/harvest/status` route built to serve it has zero live callers. The fix: have the server attach its answer to the tile payload the client already fetches, and point both chips at it. Zero new requests in the auto-farm hot path.

## 3. Impact Analysis

- **Who/what is affected:** every player, on every farmable tile, in two different views. The viewport chip is the primary readiness signal in the tile view; the stats chip is the only cooldown signal in the stats view.
- **Failure modes if unfixed:**
  1. **Permanently stale chip (finding 1).** The server honours `resetPeriod`, so a record from a previous period does not block. The chip matches on `playerId` alone, so it keeps showing a countdown for a tile the player may harvest right now — and it does so *forever*, because the record is never removed, only superseded. The player is told to wait for a reset that has already happened.
  2. **A countdown to the wrong instant (finding 2).** The reset boundary is a **game** boundary (`America/New_York`, `lib/gameTime.ts:26`), computed host-locally. A browser outside that zone sees a boundary hours off, and a DST shift moves it.
  3. **A cooldown that does not exist (finding 5).** After 5 minutes the stats chip flips to "Ready to Harvest" for a tile the server will refuse for hours. The player is invited into a guaranteed rejection.
  4. **The two chips can disagree with each other and with the button**, because two rules exist and the server is a third.
- **Blast radius of the fix:** direct — one new field on the tile payload, one server-side enrichment at the `getTileAt` seam, two chip re-points, one type, tests. Transitive — the new field is **additive and optional**, so every existing consumer of `Tile` is unaffected when it is absent; no route, schema, payload shape, or auth model changes. The one behavior change is that the chips stop lying.

## 4. Five Questions

| Question | Answer |
| -------- | ------ |
| Works for ALL cases, not just the common case? | **Yes.** The client stops deciding anything: no `playerId` matching, no `setHours`, no local cooldown constant remains. There is no branch left to get wrong — the only inputs are the server's own `canHarvest` / `timeUntilReset` / `resetPeriod`. Correctness for a stale-period record, a DST shift, a non-NY browser, and a midnight-crossing tile are all the same case: *the server said so*. |
| Scales (design tolerates growth; harness reference is 1000 agents)? | **Yes.** A third chip, a new terrain, or a new reset rule needs no client change — the field is computed by `getHarvestStatus`, which already reads the rule from one place. | Sets the standard for the industry? | **Yes.** "The client renders the server's verdict; it never re-derives one" is the same standard Gate 1 (routes have callers) and Gate 4 (schema consumers) already apply here, applied to a game rule. |

## 5. Proposed Fix (GREEN)

One field, added where the tile is already built; two chips re-pointed at it; the two invented rules deleted.

- **Approach:** compute the server's answer at the seam every tile-serving path already crosses, and ship it **on the tile payload the client already fetches**. The chip then has nothing to decide. The alternative — reviving `GET /api/harvest/status` and polling it — was **measured and rejected** (finding 11): the per-IP rate-limit counter is shared across every route, so a per-tile poll spends the same budget `/api/move` and `/api/tile` already use at VIP pacing. Riding the existing payload adds **zero** requests and cannot be throttled into a stale answer by a busy auto-farm.
- **Alternatives considered:**
  1. *Revive `GET /api/harvest/status` + a polling hook (the obvious fix).* Rejected on measurement (finding 11), and it would keep finding 7 alive — an unauthenticated `?username=` oracle. Polling also makes the answer **lag** the tile, which is the defect's cousin.
  2. *Compute correctly client-side using `lib/gameTime.ts` + the missing `resetPeriod` term.* Rejected: it re-implements the server's rule a fourth time, in the one place the protocol has been most recently burned by exactly that (FID-20260927-001, seven copies of the farmable set). "Compute the same answer locally" is not "read the server's answer", and it would still need `getCurrentResetPeriod` re-exported to the client.
  3. *Client-side only, keep the flat 5-minute rule in `TileHarvestStatus`.* Rejected: finding 5 — the rule does not exist server-side; there is nothing to preserve.
  4. *Delete the chips.* Rejected: both are live and informative once truthful; deleting UI is a bigger product decision than correcting it, and the operator directed a fix, not a removal.
